# Codex Local Remote 远程接管稳定性复盘

> 记录日期：2026-08-03（UTC+8）
>
> 结论：**存在多次真实成功，但没有达到可重复、可无人值守的稳定性交付标准。**
>
> 当前决策：停止沿现有补丁链继续重启；保留源码、提交和证据，日常使用原生 Codex。

## 1. 这份记录解决什么问题

这不是一份“所有尝试都失败”的报告。历史中存在代码验证成功、公开发布成功、
后台链路成功和真实重启成功。最终封存的原因是：这些成功没有形成可以稳定复现的
产品能力，后续仍多次出现半切换、超时、回滚、失联或需要人工启动原生 Codex。

本文回顾了三个历史 Codex 任务和最终收尾任务，时间范围约为
2026-07-25 至 2026-08-03。为满足公开仓库边界，本文不记录任务 ID、真实公网地址、
私人截图、会话原文、本机用户名或运行日志。精确来源索引只保留在本机项目的忽略目录。

本文用于：

- 防止未来把“测试通过”“已登记候选”或“单次成功”再次误写成稳定发布；
- 保留已经证明有效的设计和修复，不因最终封存而抹掉成果；
- 规定若将来重启项目，必须先满足的架构、验收和止损条件。

## 2. 证据分层

本项目曾同时出现“测试全绿”和“真实重启失败”。未来所有结论必须标出证据层级：

| 层级 | 含义                       | 能证明什么                                      | 不能证明什么                   |
| ---- | -------------------------- | ----------------------------------------------- | ------------------------------ |
| E0   | 对话中的报告或判断         | 需求、现象、用户体感                            | 根因或当前运行态               |
| E1   | 源码、单测、静态检查、CI   | 候选代码满足已覆盖的契约                        | 已安装、已接管、长期稳定       |
| E2   | 不可变运行代登记和身份回读 | 候选已正确安装、可被选择                        | 当前进程已采用该候选           |
| E3   | 单次真实运行证据           | 某次 Desktop、Broker、Sidecar、公网链路确实工作 | 下一次、睡眠后、更新后仍能工作 |
| E4   | 重复恢复与长期观察         | 产品具备可重复恢复能力                          | —                              |

正式稳定性发布必须达到 E4。E1、E2、E3 都是必要证据，但不能单独替代 E4。

## 3. 成功账本

以下成功应被保留，不能因最终结论而一概否定：

### 3.1 产品与发布成功

- v0.1.1 曾被用户实际使用并评价为可用；Windows 重启和快捷方式路径也曾成功（E0/E3）。
- v0.1.2、v0.1.3、v0.1.4 和 v0.1.5 均形成了公开版本，说明仓库构建、发布、
  安全扫描和大部分产品功能不是空壳。
- v0.1.5 的公开提交通过了 1771 项测试、公开安全检查和 Chromium 响应式验收（E1）；
  独立审查当时也未发现该发布差异中的 P0/P1。
- 活跃任务期间仅滚动更新公网 Sidecar 的方案在代码与测试层闭环，避免把
  Desktop、Broker 和 app-server 一起重启。

### 3.2 真实运行成功

- 2026-07-28 的一次冷启动中，新运行代、Broker、Sidecar 和 Desktop 均完成
  接管，本机 Broker、Sidecar、公网 API 均返回 200，且
  `desktopConnected=true`。该轮的连接核心成功，但仍有可见终端和通知未显示，
  因此结论是“连接成功、启动体验未通过”（E3）。
- 后续 v0.1.2 历史中至少有两段真实 Remote 接入：一段 Remote Desktop 成功接入
  共享 Broker 后约十分钟再次分叉；另一段有明确的
  `launched-remote / remote-attached` 回执，Desktop、Sidecar、Broker/upstream
  在线且本机、公网均为 200。后者随后仍因普通 Desktop 重启/掉线恢复未闭环而失效。
- 后续任务历史中，用户在多个不同时间明确确认“刚刚重启成功”“成功重启”
  “似乎这次重启没什么问题”“已经成功重启”或收到“远程已经正常启动”的系统通知。
- 用户在封存前总结，累计约有 5 次重启成功（E0）。该数字属于用户汇总，未通过独立
  时间审计重新计数，但足以证明方案不是完全不可运行。

### 3.3 工程成果

- 建立了 loopback-only Broker、认证 Sidecar、共享 app-server owner、不可变运行代、
  事务登记、失败回原生和公开安全检查等正确基础。
- 大量移动端、消息、附件、审批、计划、目标、历史、子智能体和中文产品界面缺陷
  得到修复或获得了定向回归保护。
- 真实失败留下了运行代、owner、intent、lease、preparation、端口和阶段回执，
  后期能够把“看起来卡住”逐步收敛到确定的 Windows 生命周期问题。
- 原生 Codex 的 fail-open / fallback 路径多数时候保住了基本可用性；最终用户也能
  通过手动原生启动恢复工作。

这些成果说明失败类型是“稳定性交付失败”，不是“功能从未实现”或“项目毫无价值”。

## 4. 时间线与结论变化

### 阶段 A：v0.1.0 / v0.1.1 建立可用基线

- 基础远程浏览、消息、文件和移动端能力形成；v0.1.1 主观使用体验较好。
- 独立终审随后指出：selected runtime 不等于 active runtime，运行中的旧任务可能
  继续复用旧 Broker；`started` 队列恢复、端口配置、幂等键和 Supervisor
  stop/start 竞态仍未闭环。
- 这一阶段的正确结论应为：产品功能可用，长期生命周期仍为 BLOCK。

### 阶段 B：v0.1.2 缺陷修复扩大为启动架构改造

- 原计划是修复 v0.1.1 的缺陷，实际同时引入原生默认启动、显式 AI 授权接管、
  不可变运行代切换、后台预备和 attach-only 等架构改造。
- UI、移动端、目标、暂停、引导、历史、图片、附件和连接提示等产品问题继续进入
  同一发布门，导致“重启核心”与大量小改动强耦合。
- 候选代码多次通过上千项测试，但真实 Open 仍会在新的 Windows 边界失败。

### 阶段 C：基础设施优先与多次单次成功

- 团队识别出“先关闭 Desktop，再切运行代”会把失败成本直接转嫁给用户，改为：
  先在 Desktop 不动时准备后台，最后只做 attach。
- 该方向带来真实成功；至少一次冷启动获得完整连接 200，也有多个后续时段由用户
  确认重启成功。
- 但成功没有连续复现。不同现场状态会暴露新的 selected/active、任务、进程、
  权限、模块或回执问题。

### 阶段 D：版本推进到 v0.1.5，但采用证据滞后

- v0.1.3 至 v0.1.5 继续修复产品和热更新问题，v0.1.5 已公开发布。
- 当时公开提交、CI、浏览器验收和独立审查通过，但当前机器的公网进程尚未采用新
  候选。发布完成早于一次完整真实切换，顺序错误。
- 用户明确指出：一个版本不能在没有至少一次真实切换成功时先宣布发布完成。

### 阶段 E：v0.1.5 后的九次本地加固仍未闭环

- v0.1.5 之后，`main` 又累计 9 个未推送修复，覆盖继承监听、原生命令行查询、
  端口迁移、跨权限 owner、模块绑定、app-server 身份、超时、owner lease 和
  脱离 Desktop 作业的控制器。
- 最新本地候选提交为 `5e924d8`。定向测试通过（E1），但真实接管仍没有成功验收，
  因而没有 E3/E4 证据。
- 封存时的记录为：公网 ready 返回 502；安装态为
  `inactive / RemoteState=unverified / TaskState=Ready`；交接回执停在
  `running / desktop-attach`；用户必须手动原生启动。

### 阶段 F：停止继续重启

- 当前任务回读到 80 个 turn、192 条用户消息；其中 80 条涉及重启、切换或接管，
  44 条涉及耗时。该自动计数包含重复短消息，只用于说明沟通和操作负担，不等于
  独立工时统计。
- 用户最终报告累计投入超过 100 小时、约 5 次重启成功。成功率和恢复成本均不符合
  日常工具要求。
- 最终决定：停止现有补丁路线，保留原生 Codex，冻结自动远程控制入口。

## 5. 技术故障链

这不是一个未修好的单点 Bug，而是一组跨进程生命周期问题串联。每修完一层，真实
Windows 现场又暴露下一层。

### 5.1 selected、active 和 running 被混为一谈

- pointer 或计划任务定义已经指向新运行代，不代表正在运行的 Bootstrap、Broker、
  Sidecar 已采用它。
- 任务处于 `Running` 且采用 `IgnoreNew` 语义时，旧启动器会复用旧 Broker，导致自然
  重开 Desktop 仍连接旧代。
- 早期状态和发布说明曾把“已选中/已登记”表达得过于接近“已接管”。

### 5.2 关闭 Desktop 之前仍有高风险工作

- 旧流程在关闭 Desktop 后才切 pointer、任务或后台运行代；任一后置步骤失败，用户
  先失去 Desktop，再得到失败回滚。
- 后来虽然改为 infrastructure-first，准备态的 readiness、Sidecar receipt、
  Desktop-detached 语义和任务描述仍多次不一致。
- attach-only 没有一开始就成为一个真正独立、最小、可证明的末端操作。

### 5.3 控制器与被关闭的 Desktop 同生共死

- 最终确定的一条根因是：执行 Open 的控制进程仍在即将被关闭的 Desktop 作业树中。
  Desktop 一关，负责继续接管和写最终回执的进程也退出。
- 更早的实现还出现过 coordinator 在自己所属的计划任务中停止该任务、worker 以
  `WorkerPid=0` 发布后再回写造成快速子进程拒绝 claim 等同类 owner 生命周期问题。
- 结果是新 Desktop 未被可靠拉起，回执长期停在 `desktop-attach/running`，用户只能
  手动启动原生 Codex。
- `5e924d8` 把控制器改成 Task Scheduler 的独立一次性 worker，并补了旧回执清理，
  但只取得代码和定向测试证据，尚无 E3/E4 实机闭环。

### 5.4 Windows 进程树和监听句柄不是简单 PID 问题

- app-server 根进程退出后，`conhost.exe` 或工具后代可能继续持有继承的上游监听。
- Electron 根退出后也可能残留 ChatGPT 子进程；切换屏障要求“全部 ChatGPT 进程为零”，
  因而在用户已经失去旧窗口后立刻失败。
- TCP 表可能仍显示已经死亡的创建 PID，按 PID、进程名或父子关系继续清理存在误杀风险。
- 旧上游端口因此成为“能连接但无法证明 owner”的幽灵端口，新运行代按安全策略拒绝接管。
- 后续实现了精确进程树快照、原生命令行读取、连续空端口观察和离线原子端口迁移；
  但这些加固也扩大了交接状态机和回滚组合。

### 5.5 跨权限和模块版本导致现场与测试不同

- 高权限任务中的进程命令行可能被 CIM 隐藏；普通进程无法证明 owner，导致安全门失败。
- 新脚本调用新增参数时，独立 PowerShell 进程可能仍解析到旧运行代的同名模块，出现
  “参数不存在”。
- 更新 `Highest` 计划任务时还出现过普通权限路径的访问拒绝。
- 这些问题在普通单进程 fixture 中不容易复现，必须用真实跨进程、跨完整性级别测试。

### 5.6 intent、lease、preparation 和 receipt 状态过多

- selected/previous/active、Native/Remote、preparation、owner lease、handoff intent、
  supervisor receipt 和补偿状态之间存在大量组合。
- 旧 `attaching` 或 `running/desktop-attach` 回执会阻塞下一次恢复；清理它又必须防止
  删除较新的合法 intent。
- 120、180、240、300 秒等多个等待预算曾在不同层不一致，产生“内层仍可能成功，
  外层已经补偿回原生”的假失败。
- 状态机复杂度已经超过当前测试和审计能够经济覆盖的范围。

### 5.7 消息与任务恢复问题增加了远程可用性风险

- `started` 队列项早期未纳入重启对账，Sidecar 在响应窗口崩溃后可能留下
  `started + paused`，阻塞后续消息。
- 人工重试若生成新幂等键，服务端已经执行但响应丢失时可能重复副作用。
- 目标暂停/继续、引导发送、附件上传、断线提示和公网发送按钮等问题多次出现，说明
  远程链路除了“能启动”，还必须证明消息可见性和恢复语义。
- 某些现场曾同时存在原生 Desktop app-server 与受管 Broker/app-server 两套事件流，
  电脑消息和手机消息落入不同 owner；这会表现为漏消息、假运行状态或公网 503。

## 6. 过程与产品决策失误

### 6.1 v0.1.2 范围失控

缺陷修复、UI 优化、原生默认启动、AI 授权、运行代切换、公网热更新和最终发布被放进
同一个里程碑。小改动持续进入全量验收，核心重启架构则不断被新需求和回归打断。

### 6.2 过早用 E1/E2 语言描述 E3/E4

多次出现“测试全绿、候选已登记、审计 PASS”之后，真实接管马上失败。技术陈述常常
带有证据限定，但总体语气仍让用户合理预期“下一次就是最后一次”。这是沟通和发布门
设计的共同失误。

### 6.3 发布顺序错误

v0.1.5 在真实当前机器尚未采用候选时先完成公开发布。代码发布本身真实成功，但对一个
以本机接管为核心的产品，至少一次当前版本的实机切换应当位于 tag/release 之前。

### 6.4 把用户当成重复冷启动测试器

多个周期都采用“长时间修复和审计 → 请求授权 → 真实切换立刻暴露新问题”。即使每次
失败点不同，用户体验仍是同一个失败循环。主力开发机不应承担架构探索的重复破坏成本。

### 6.5 缺少早期硬止损

项目虽多次口头承诺“只尝试一次”“失败就停”，但新的确定根因出现后又继续修复、登记
和尝试。没有在 30、50、70 小时等节点真正执行架构暂停和重新立项。

### 6.6 审计和上下文膨胀

审计、子智能体、全量测试和版本文档本应降低风险，实际有时扩大了上下文、延迟公网更新，
甚至让“有活动任务时不能切 Sidecar”的旧门长期无法归零。当前任务本身也变成超长任务。

### 6.7 用户的基本可用性优先级没有始终置顶

当用户明确即将离开电脑、需要公网立刻可用时，流程仍被 CI、登记、门禁和新的修复占用。
正确产品决策应是优先保住一个已验证入口；无法及时恢复时，应明确停止并让原生 Codex
稳定可用，而不是继续给乐观时间估计。

## 7. 不应归入产品失败的事项

- 某个旧 Codex 开发任务达到约 258K 上下文后反复压缩，是 Codex Desktop/app-server
  宿主任务问题，不是 Local Remote 网页或远程同步缺陷。
- 当时界面中的 `43%` 是七天额度剩余，不是上下文比例。
- CI runner 的个别超时有一部分确为资源抖动；只有稳定单独复现的超时才应归为项目问题。
- 用户主动关闭、系统卡死、Codex 更新或账号切换不是同一种事件；只有项目无法在这些
  正常生活周期后可靠恢复，才属于本项目的产品稳定性问题。

## 8. 封存时的精确边界

### 已确认

- 公开远端最后确认版本为 v0.1.5，远端默认分支位于 `c3a0771`。
- 本地 `main` 位于 `5e924d8`，比远端多 9 个运行时交接修复提交。
- 这 9 个提交未进行最终真实接管验收，不能称为 v0.1.6 或已发布修复。
- 封存前最后一次现场记录显示公网 502、安装态 inactive/unverified、任务 Ready、
  交接回执卡在 desktop-attach；原生 Codex 由用户手动恢复。
- Agent 远程控制入口在封存时被标记为不可用，防止未来自动触发同一重启链。

### 未确认

- `5e924d8` 的独立一次性 worker 是否能在干净实机上稳定完成一次接管；没有真实证据。
- 九个未发布提交组合后的回滚、睡眠、Windows 重启、Codex 更新和账号切换稳定性。
- 当前机器未来状态；本文记录的是封存时快照，不是持续健康监控。

## 9. 若未来重启项目，必须先满足的准入条件

未来工作不得从“再试一次 Open”开始。必须作为新架构任务重新立项，并逐项满足：

### 9.1 架构准入

1. 交接控制器从设计上独立于 Desktop、app-server、Broker 和 Sidecar 的作业树；
   关闭任何被管理对象都不能关闭控制器。
2. Desktop 关闭后的路径只能做三件事：验证精确 intent、启动精确 Desktop、写最终回执。
   不得在此阶段切 pointer、改任务、换端口、升级模块或重启后台。
3. 把 selected、prepared、active、attached 和 compensated 定义成最小、单调、可恢复的
   状态机；删除无法证明价值的中间状态。
4. 每个状态写入都必须带 generation/intent ID、compare-and-swap 和明确过期规则；
   不能靠“看起来旧”删除回执。
5. 成功和失败都必须自动回到唯一稳态：Remote ready 或 Native usable。不存在无限
   `running`、无限等待或“需要用户猜是否结束”。

### 9.2 隔离验证准入

1. 先在一次性 Windows VM 或专用测试账户完成循环测试，不再用用户主力 Codex 任务
   探索生命周期缺陷。
2. 覆盖真实 Job Object、Task Scheduler、UAC 完整性级别、PowerShell 新进程模块解析、
   console 后代和继承 socket handle；不能只用 fixture 模拟 PID。
3. 在隔离环境至少覆盖：原生→远程、远程幂等 Open、Close→原生、活动任务、空闲任务、
   Sidecar 热更新、睡眠恢复、Windows 重启、Codex 更新、账号切换和失败补偿。
4. 隔离环境完成连续循环后，主力机只允许一次最终授权接管，不再让用户重复承担测试。

### 9.3 发布准入

发布顺序固定为：

1. E1：聚焦回归、全量检查和公开安全扫描通过；
2. E2：从干净提交登记不可变运行代，并回读 exact commit / manifest / task；
3. 关闭 Desktop 前，后台准备、进程 owner、unknown/unsafe、端口和回执全部通过；
4. E3：一次受控 attach 在硬时限内成功，本机与公网 ready=200，Desktop 显示远程连接；
5. 真实发送、引导、停止、目标、附件上传下载、断线重连和手机可见性通过；
6. E4：隔离环境的重复恢复矩阵通过，且主力机经历约定观察期无自动回退；
7. E1 后可以 normal push 明确标注为 unreleased candidate 的提交，用于固定候选、
   远端备份、协作和审计；只有 E4 通过后才允许 tag、release 或稳定发布声明。

任何一步失败：自动恢复 Native，保存精确证据，停止本轮。不得在同一用户会话内顺手修完
后再次关闭 Desktop。

### 9.4 时间与沟通准入

- 单次主力机交接从 Desktop 关闭到明确结果应有一个短硬上限；超时必须回原生并结束。
- 不再承诺“最后一次重启”，除非 post-close 路径已经在隔离环境逐字节等价验证。
- 每次汇报必须同时写证据层级和剩余门，例如“E2 已通过，E3 未执行”。
- 发现新架构根因时，不得自动把任务变成新一轮修复；先暂停、更新风险和重新授权范围。
- UI 小改动使用聚焦回归，不得重新打开完整发布门；启动核心未稳定前也不得把新 UI
  需求继续并入同一发布。

## 10. 可复用的失败判定

未来出现任一情况，应立即判定本轮失败并停止，而不是继续等待：

- 控制器与 Desktop 同时消失；
- 回执超过硬时限仍为 running/attaching；
- selected、task、active runtime 或进程模块来源不一致；
- 任何受管端口存在无法证明 owner 的监听；
- 新 Desktop 已启动但旧根仍存活，或出现两个候选 owner；
- 公网壳为 200，但执行 ready 非 200 或 Desktop 未连接；
- 需要手动原生启动才能恢复；
- 成功只存在于测试、CI、候选登记或通知，没有同一轮真实消息证据。

## 11. 未来仍可复用的资产

- Broker/Sidecar 的安全边界、认证、公开安全扫描和文件权限模型；
- Web 产品功能及其移动端、消息、附件、目标和历史回归；
- 不可变运行代构建与 `-NoStart` 登记思路；
- Sidecar 与 Broker/Desktop 解耦的热更新方向；
- Windows owner、端口、intent、lease 和回执诊断工具；
- 失败回原生的产品原则。

不应直接复用的是当前 Open 状态机和九个未发布提交的整体组合。它们可以作为反例、测试
素材或新设计的参考，但在新的 E3/E4 证据出现前不能恢复为自动控制入口。

## 12. 最终结论

Codex Local Remote 证明了远程产品方向和大量功能是可行的，也取得过多次真实重启成功。
失败的是当前 Windows 快速接管方案的**可重复性、恢复成本和发布纪律**。

因此最准确的封存表述是：

> 项目存在真实成功和可复用成果；但截至 2026-08-03，远程接管无法在日常 Windows、
> Codex 更新、睡眠/重启和长任务条件下达到稳定、无人值守、可预测的 E4 标准。
> 当前补丁路线停止，未来只能以重新设计和隔离验证为前提恢复。
