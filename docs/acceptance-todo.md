### 最终产品与施工契约

- [~] **默认永远原生**：普通 ChatGPT 启动、Codex 更新、Windows 重启及
  睡眠恢复后均使用 vendor 原生入口，不自动启用远程、不自动重开 Desktop，
  也不依赖用户点击专用快捷方式。代码、计划任务零触发器和故障注入已完成；
  2026-07-30 用户又执行了一次真实 Codex 更新，只读回读为
  `LaunchMode=native-only`、task `Ready`/not running、Broker not ready、
  `DesktopConnected=false` 及 package `update-pending`，证明更新没有自动接管
  或重开 Desktop。仍需在安装当前不可变候选后验证显式 `Open`，并随后以普通
  启动、睡眠和 Windows 重启现场证据关闭本项。
- [~] **“打开远程”是唯一接管授权**：任意 AI 必须把这句话路由到同一个稳定、
  已安装、幂等的控制入口。若已 `remote-ready`，立即返回且 Desktop、
  Broker、Sidecar 重启数均为 0；若仅 Web/Sidecar 缺失，先补齐公网层且
  Desktop/Broker 重启数为 0；只有当前 Desktop 为原生进程且不能热注入共享
  owner 时，才允许外部控制器受控重开 Desktop 至多一次。dispatcher 与
  `Open` 状态转换/补偿测试已通过；固定全局 skill 尚待随 clean commit 安装，
  真实幂等与采用仍待现场。
- [~] **受权立即重启不再分裂成两个锁窗口**：detached worker 只把 exact
  pointer/manifest/desired-mode intent 交给 stable dispatcher；dispatcher 在同一
  DataDir control mutex 内完成 intent 前置回读、精确 package path + PID/creation
  identity 停止、task `Ready` drain、intent 后置回读和 installed `Open`。取消意图
  为零 stop，post-stop supersession 进入原生补偿；空路径、同名外部进程及 PID
  creation drift 均失败关闭。24/24 定向行为测试和完整仓库测试通过；用户明确把
  新路径的真实重启耗时/现场采用留到后续验收，本轮不触碰当前 Desktop。
- [~] **“关闭远程”不破坏当前任务**：立即关闭公网入口并清除远程意图，不重启
  Desktop。已经通过 Broker 工作的当前 Desktop 可安全运行到自然退出；下一次
  普通启动回到原生。若将来要求立刻把当前进程也改成原生，必须另获明确的
  Desktop 重开许可。定向事务与失败补偿已通过，当前运行态尚未执行真实
  `Close`。
- [~] **施工分层更新**：修复 Web/Sidecar 后可以独立部署并有界重启公网层；
  Desktop 和持有 app-server 的 Broker 是长寿命 owner，施工期间不得启停。
  若当前 Desktop 已回到原生，公网 `/ready=503` 是真实的 fail-closed，
  不能为制造绿色状态而另起第二个 app-server owner。Sidecar/Web 热更新及
  rollback 定向回归已通过；真实同租约采用待远程连接后验收。
- [~] **失败一次即停且回到可理解状态**：控制器不得循环拉起、反复 UAC、反复
  重开 Desktop 或用绿色“已启动”掩盖 native fail-open。任何阶段失败都必须
  有结构化阶段/原因，撤销本次远程意图，恢复原生可用性，并保留可在线修复的
  后台诊断；再次尝试必须来自新的显式“打开远程”。故障注入覆盖 Sidecar、
  Broker、Desktop、登记和启动失败；真实控制反馈仍待当前候选采用。
- [~] **入口跨版本稳定**：全局规则/skill 只调用固定的已安装 dispatcher，
  dispatcher 再解析当前不可变运行代；源码目录、旧 selected pointer、旧
  package 路径和快捷方式都不能成为长期单点。注册、升级和卸载必须事务化，
  不覆盖 foreign dispatcher，并能精确回滚自己的 task、pointer、receipt
  与文件。安装/升级/卸载及 manifest 兼容性自动化已通过，固定安装态尚待
  clean commit 后建立。
- [~] **旧快捷方式名称不再形成第二套启动链**：受管“安全启动”只可作为固定
  dispatcher 的可选显式 `Open -AllowDesktopRestart` 别名；不得直接绑定
  Desktop、源码目录、selected runtime 或旧 launcher。普通 vendor 入口始终
  原生，日常打开远程也不要求用户亲自点击快捷方式。快捷方式安装事务和
  CP437/非 UTF-8 PowerShell 5.1 回显 `11/11` 已通过，真实链接待安装后回读。
- [~] **任意 AI 的权限适配只有一次执行体**：`Status` 直接只读；`Open` /
  `Close` 在调用前判断当前 token，管理员直接调用，非管理员通过已启用的
  Windows `sudo` 一次调用同一 dispatcher。禁止 dispatcher 内部再派生
  `RunAs`、先失败后重放或形成第二个 mutex/intent；提权不扩大 Desktop
  重开授权。skill 源码与验证已完成，尚待只暂存其精确全局规则行、安装
  junction 并用当前 token 实测。
- [~] **无人值守边界**：候选封存前持续后台实现、定向测试、文档和审查，不要求
  用户陪同，也不重启 Desktop/Broker。只有最终代码、不可变运行代、安装态和
  自动化均已封存，而真实采用仍物理上需要重开 Desktop 时，才报告一次明确
  采用门；不得用多次重启探索根因。当前施工期间 Desktop/Broker 启停数保持
  0，尚未进入可能的一次采用门。

### 过去长时间未收敛的根因与纠偏

1. 旧实现把“登记候选、选择运行代、启动后台、接管 Desktop、恢复公网、验收”
   混在一条启动脚本里；一个阶段失败会改变后续现场，导致下一轮诊断面对不同
   owner，而不是同一可重复反例。
2. `selected`、`active`、`ready`、任务 `Running` 和 Desktop 可用曾被误当成
   同一个成功状态；自动化代码通过不等于不可变运行代已采用，更不等于三端同一
   thread/turn。
3. 自动接管、快捷方式唯一 owner 与最新“默认原生、按需远程”合同冲突。继续在
   旧合同上补 drain、UAC、fail-open 和计划任务恢复，扩大了状态空间，也让 Codex
   更新、睡眠和重启成为重复风险源。
4. 施工把真实冷启动同时当作部署手段和调试手段，造成用户至少多次陪同重启；
   后续必须先用纯函数/fixture/事务故障注入封存，再执行唯一真实采用。
5. 长时间批量修复和反复宽测试延迟了用户可验收版本；今后按 owner 分层，定向
   回归先闭合根因，完整 `check`/`check:public` 只在最终树运行一次。
6. 进度沟通没有先给出“是否还要重启、当前是否成功”的明确结论。这是交付流程
   缺陷；运行态判断必须先报告 `native / remote-ready / degraded / transition /
blocked`，再继续后台工作。
